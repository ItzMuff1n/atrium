## 1. `hermes verify --json` — PASS

The project's own verification recipe. Recipe loaded from
`.hermes/environment.json` (`build: cargo build`, `test: cargo test`).

```
recipe: atrium-resolver (CLI, no server)
ok    : True
  build  exit=0 ok=True
  test   exit=0 ok=True
readiness: None
```

**Note on an earlier failing run.** The first `hermes verify` run reported
`ok: false`. The build and test phases both passed; the failure was the
readiness poll, which sat waiting for a web server at `http://127.0.0.1:8000/`
for 60 seconds and got `Connection refused`. That poll was testing something
this project does not have. The auto-detector saw `Cargo.toml` and guessed
`cargo run` was a server start command; `atrium-resolver` with no arguments
prints its usage and exits. The saved recipe has had `start` set to `null`, and
`hermes verify` now passes. **This was a fault in the detected recipe, not in
the resolver.**

## Scripting bug found and fixed during this work

The first version of `hand-test.sh` generated the long-path test case with
`printf '/%0.sa' $(seq 1 300)`, which repeats the whole string `/a` three
hundred times — a 600-character path of 300 `/a` components — instead of
building one 300-character name. It was testing the wrong thing, and the
rejection it produced (`/a does not exist`) came from the missing first
component, not from any length handling.

Fixed to `"/$(printf 'a%.0s' $(seq 1 300))"`. Re-run output now:

```
301-char single component   REJECT  OS refused: File name too long (os error 36)
400-char / 200 components   REJECT  `/a` does not exist inside root
256-char single component   REJECT  `/c` does not exist inside root
255-char single component   REJECT  `/b` does not exist inside root
```

The OS-level length rejection is now genuinely exercised, and the resolver
returns its own named reason rather than leaking an error.

## What is NOT verified

**Muffin's hands-on pass.** Everything above is agent-run. BUILD-PLAN requires
the *user's* verification for Phase 1, and no amount of agent-side running
substitutes for it. Phase 1 remains unsigned.

**The three NUL-byte lines in section F.** A command-line argument is
terminated by a NUL byte, so the shell refuses them before `atrium-resolver`
sees the string. They are covered only by `cargo test`
(`section_f_unicode_and_lookalikes`, `section_h_nasty_combinations`), which
calls the resolver in-process and can hold a NUL. Recorded in `attack-list.md`
section F.

**Whether a replacement after streaming reaches the screen** — unrelated to
Phase 1; noted only so it is not lost.
