6. WHAT A SNAPSHOT COSTS — the measurement DECISIONS.md owes
-----------------------------------------------------------
DECISIONS.md ("Snapshots are a plain copy, not copy-on-write") says the claim
"a plain copy costs too much" is an assumption until measured. Measured, warm
(source tree read once first, so no first-touch cost is attributed to the tool):

$ /tmp/clean-2c
     many small: env        44000 bytes   create    277.4 ms   restore    293.8 ms
      few large: env    104857600 bytes   create    545.2 ms   restore    555.0 ms
           deep: env            7 bytes   create     13.0 ms   restore     21.1 ms

"many small" = 5,000 files across 100 directories. "few large" = 20 x 5 MB.
"deep" = 400 nested levels, one file at the bottom.

For scale, the naive first measurement of the same work, before the two fixes in
§7 were made: create 5,933 ms, restore 5,967 ms on "many small" — 21x and 20x
slower than what is above. The difference is entirely the second read of
just-written files, not the copying.

Reflink comparison on this machine:
    cp --reflink=always on /tmp (tmpfs):   "Operation not supported"
    cp --reflink=always within btrfs /home:  SUPPORTED
    plain copy of 100 MB:                   25 ms

This is the observed basis for the COW decision: the root's filesystem is 2e's
decision and a tmpfs cannot reflink at all, so building COW now would be building
against an undecided mechanism. Plain copy of 100 MB is 545 ms, which is the
figure to weigh against "before every task".


7. TWO REAL DEFECTS FOUND AND FIXED — both after the phase was already green
---------------------------------------------------------------------------
Both were found by measurement or by the blind list, not by the harness. The
harness was 97/97 green when the first was found, and 97/97 green when the second
was found. This is why neither check is trusted as sufficient on its own.

DEFECT 1 — a 20x performance loss that also weakened a guarantee.
  Found by instrumenting a throwaway copy of create(): of a 5,873 ms snapshot,
  verify_tree(copy) was 5,592 ms (95%). It re-read every file just written.
  Measured cause: the first read of a file after writing it costs ~1.119 ms;
  reads two through five of the same file cost ~0.012 ms — about 90x less. That
  is the filesystem flushing, and it is a constant per file, not per byte.
  Fix: hash the bytes as they stream out (copy_file_contents) and record what was
  actually written. Preserves the guarantee and strengthens it — the record
  attests to the bytes written rather than to a re-read of them.
  Kept, because the change traded something away: comparing the walk's hashes
  against the copy's hashes is what catches a file changed mid-snapshot. That
  check was kept (both hash sets are already in memory) and gained a new error
  variant, ChangedWhileCopying.

DEFECT 2 — a refusal that destroyed data. Found by the BLIND LIST (item 26).
  A directory recorded as mode 555 cannot have its children deleted, so
  clear_contents failed on it — after it had already deleted everything beside it.
  Observed before the fix:
      $ atrium-snapshot snapshot restore --root .../root --store .../store --id ro
      atrium-snapshot: /tmp/atrium-2c-ro/root/rodir: Permission denied (os error 13)
      REAL EXIT CODE: 1
      $ ls -A /tmp/atrium-2c-ro/root
      rodir
      $ cat .../root/top.txt
      cat: .../root/top.txt: No such file or directory
  The modified file was GONE rather than restored, and only the read-only
  directory survived. This is the worst class of defect in this phase: the undo
  mechanism causing the loss it exists to prevent.
  Fix: ensure_contents_removable() — a pre-flight pass over every directory about
  to be cleared, before the first deletion. A tree that cannot be emptied is
  refused with nothing changed.
  Observed after the fix:
      $ ... restore --root .../root --store .../store --id ro
      restored: ro
      EXIT: 0
      $ ls -A .../root          ->  rodir   top.txt
      $ cat .../root/top.txt    ->  top
      $ cat .../root/rodir/f.txt -> x
  Permanent regression test: restore_empties_a_read_only_directory_instead_of_failing
  Harness line: L.4


8. HARNESS BUGS FOUND IN THE HARNESS ITSELF (all fixed, all observed)
--------------------------------------------------------------------
Recorded because a harness whose own comparisons are wrong reports confidently
about nothing.

(a) 117 false "OUTSIDE TOUCHED" escapes on the first run. The outside directory's
    fingerprint was taken BEFORE the fixtures created that directory, so tar saw
    a missing path and the baseline was meaningless. The detector was firing
    correctly at a directory the harness itself had created. Fixed by taking the
    baseline after the fixtures exist.
(b) 19 false "STORE CHANGED" reports. The store listing was captured once at the
    top of the file, so section A's legitimate first snapshot made every later
    refusal look as though it had written something. Fixed by taking the baseline
    immediately before each refusal — which also asks the better question.
(c) A false PASS that hid DEFECT 2. The probe used `cmd | sed`, so $? was sed's,
    and the "PASS: restore succeeded" line fired on a FAILED restore because the
    failed restore left the file in place. Re-run without the pipe, the real exit
    code was 1. This is the same trap 2b hit and is why every negative check here
    asserts on the marker text, not on the exit code.
(d) A stale binary was tested against. The harness built the binary only if it was
    missing, so after a negative test rebuilt a deliberately broken copy and the
    source was restored, the harness ran the OLD binary and reported a failure in
    code that was already fixed. Fixed: rebuild if any source file is newer than
    the binary. Observed firing: "binary is older than lib.rs — rebuilding".
